# Phase 2 : API Fastify — Plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use inline-one-shot-execution (choisi par l'utilisateur) ou superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** Une API Fastify qui couvre tout ce que fait le monolithe : authentification,
les 50 actions d'écriture et toutes les lectures des pages, avec des tests d'intégration
sur un vrai PostgreSQL. Elle tourne en recette sur `api.morpion.cloud`, joignable
seulement par Cloudflare Tunnel, à côté du monolithe qui reste en service.

**Spec :** `docs/superpowers/specs/2026-10-17-separation-front-api-pwa-design.md` (§4, §5, §8).

**Tech Stack :** Fastify 5, `@fastify/cookie`, `@fastify/cors`, `@fastify/rate-limit`,
`@fastify/multipart`, zod 4, pg, Vitest 5, esbuild (bundle de l'image), PostgreSQL 16,
cloudflared.

## Décisions de conception

Elles précisent ou corrigent la spec ; chacune est reportée dans la spec à la tâche 15.

1. **Un seul code métier, partagé par le monolithe et l'API : `packages/metier`.**
   La spec prévoyait de *déplacer* le SQL des 50 actions dans l'API. Mais le monolithe
   reste en production jusqu'à la phase 5 : deux copies de 2 500 lignes de règles de
   gestion (stock, crédit, codes promo) divergeraient dès la première correction. Les
   actions sont donc déplacées dans `packages/metier`, sous forme de fonctions
   `service(db, utilisateur, ...arguments)`. `lib/actions/index.ts` devient une couche
   mince (session → service → `revalidatePath`), et l'API appelle les mêmes fonctions.
   Le corps SQL n'est pas réécrit.
2. **Les lectures sont recopiées dans l'API, pas partagées.** Les 25 pages disparaissent
   en phase 5 ; les modifier maintenant coûterait plus que la duplication temporaire
   d'un code qui ne modifie aucune donnée.
3. **`db/` reste à la racine** (la spec le plaçait dans `apps/api`) : le compose et
   `server-deploy.sh` du monolithe l'utilisent jusqu'à la bascule.
4. **Secret de session distinct** : l'API signe avec `API_JWT_SECRET`, pas avec le
   `JWT_SECRET` du monolithe. Un jeton de l'un ne vaut rien chez l'autre.
5. **Erreurs** : les services lèvent `ErreurMetier(message, statut)`. L'API traduit
   `ErreurMetier` → son statut, `P0001` (exception PL/pgSQL, ex. stock insuffisant) → 409,
   `23505` (doublon) → 409, `ZodError` → 400, tout le reste → 500 avec un message
   générique et l'erreur complète dans les journaux. Le monolithe affiche toujours le
   message, comme aujourd'hui (`ErreurMetier` hérite d'`Error`).

## Global Constraints

- **Branche dédiée** `phase-2-api`, dans un worktree. Rien sur `main` avant la revue.
- **Le monolithe ne change pas de comportement.** Après chaque tâche qui touche
  `lib/actions` : `npm run build` à la racine passe et `docker build -t mb-test .` aussi.
- **Tests d'intégration sur PostgreSQL réel**, jamais sur une base simulée pour le code
  métier. Base de test : `DATABASE_URL_TEST` (super-utilisateur, base `postgres`). En
  local :
  ```bash
  docker run -d --name mb-test-pg -e POSTGRES_PASSWORD=test -p 127.0.0.1:55432:5432 postgres:16-alpine
  export DATABASE_URL_TEST=postgres://postgres:test@127.0.0.1:55432/postgres
  ```
  Sans `DATABASE_URL_TEST`, les tests d'intégration **échouent** (ils ne se sautent pas).
- **TDD** : chaque route naît d'un test qui échoue pour la bonne raison (404 de route
  absente, pas une erreur de compilation).
- **Chaque route d'écriture a au moins trois tests** : cas nominal (effet vérifié en
  base, pas seulement le code HTTP), refus de permission (403), refus de périmètre
  (boutique hors de portée, 403). Les règles métier signalées dans le code (plafond de
  crédit, stock insuffisant, code promo expiré…) ont chacune leur test.
- **Nommage** : français, commits `Préfixe : description` + ligne `Co-Authored-By`.
- **Versions** : dernières stables au moment de l'exécution ; TypeScript reste en 5.

## Review Focus

1. **Parité des permissions** : chaque service applique exactement les contrôles de
   l'action d'origine. → Tâches 6 à 11, test de refus par route.
2. **Audience des sessions** : un client ne se connecte pas au backoffice, le personnel
   ne se connecte pas à la vitrine, un cookie `www` ne vaut rien sur une requête
   `backoffice`. → Tâche 4.
3. **CSRF** : une écriture sans `Origin` autorisé est refusée avant tout traitement,
   y compris l'upload multipart (qui n'a pas de preflight). → Tâches 3 et 13.
4. **Route manquante** : chaque service exporté par `packages/metier` est exposé par une
   route. → Tâche 14 (garde vérifiée par mutation).
5. **Transactions** : un échec au milieu d'une vente ne laisse ni ligne orpheline ni
   stock décrémenté. → Tâche 6, test d'échec sur la deuxième ligne.
6. **Uploads** : pas de traversée de chemin, type et taille contrôlés. → Tâche 13.

### Task 3: Jetons, CORS et contrôle d'origine

**Files:** Create `apps/api/src/session/jeton.ts` (+ test), `apps/api/src/securite.ts`
(+ test) ; Modify `apps/api/src/app.ts`, `apps/api/src/server.ts`.

- `jeton.ts` : reprise de `signToken`/`verifyToken` (`lib/session.ts`), avec une revendication
  `aud` (`"www"` | `"backoffice"`) et le secret `API_JWT_SECRET`. Comparaison de signature
  à temps constant conservée.
- `securite.ts` :
  - `audienceDe(origine)` → `"www"` | `"backoffice"` | `null` d'après `ORIGINE_WWW` /
    `ORIGINE_BACKOFFICE` ;

  - hook `onRequest` : toute méthode autre que GET/HEAD/OPTIONS exige un `Origin` connu,
    sinon 403 avant tout traitement ; une écriture JSON exige
    `Content-Type: application/json` (sinon 415), sauf la route d'upload (multipart).
- `construireApp` reçoit la configuration en plus du pool.

### Tasks 6 à 11 : les 50 actions

Même méthode pour chaque domaine :

1. **Déplacer** les fonctions de `lib/actions/index.ts` vers `packages/metier/src/<domaine>.ts`
   (avec les helpers qu'elles utilisent, regroupés dans `packages/metier/src/interne.ts`) :
   - signature `(db: Db, utilisateur: Utilisateur, ...arguments d'origine)` ;
     `creerReservation` reçoit `Utilisateur | null` (visiteur anonyme autorisé) ;
   - `getSession()` / `exigerAccesBoutique` / `exigerAdministrateur` → gardes de `acces.ts`
     sur l'utilisateur reçu ; `pool` → `db` ;
   - `throw new Error(m)` → `throw new ErreurMetier(m, statut)`, statut 403 si le message
     refuse un accès ou un droit, 404 s'il dit « introuvable » / « non trouvé(e) », 400
     sinon ;
   - `revalidatePath` retiré du service ; **aucune autre ligne modifiée**.
2. **Monolithe** : l'export de `lib/actions/index.ts` devient
   `const r = await service(pool, await sessionExigee(), ...args); revalidatePath(...); return r;`
   avec exactement les mêmes `revalidatePath` qu'avant. `sessionExigee()` lève
   « Non authentifié » comme aujourd'hui.
3. **Schémas zod** des corps dans `packages/shared/src/schemas.ts`, alignés sur les types
   `*FormData` existants (test de type : `expectTypeOf<z.infer<…>>().toEqualTypeOf<…>()`).
4. **Routes** dans `apps/api/src/routes/<domaine>.ts`, enregistrées via le registre de la
   tâche 14 (`route(app, { methode, chemin, service, garde, schema })`).
5. **Tests d'intégration** (règles des Global Constraints) **écrits avant les routes**.
6. `npm test`, `npm run build` racine, `docker build` ; commit `Métier : <domaine>`.
